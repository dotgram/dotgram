## Which rows can see which change

A row that cannot see a change must not be read as evidence about it.

- **The lazy load** (`e2d8204e`: a dictionary's checks compile when first asked) is visible in
  exactly the two dictionary rows. Every message row uses the schema compiled into the package,
  which never passes through a dictionary — except the `Dictionary` half of the 4.4 rows, where the
  checks are the file's and are compiled on the first message of the setup, before anything is
  timed.
- **The versions** (`d0aeaeaf`, `f787f18b`) are visible only in the three rows that name them.
- **The generator's watermark** (`bfb36682`: a guarded materializer's scan is linear in depth rather
  than quadratic) **reaches nothing here, and the reason is structural rather than measured.** The
  shipped FIX parsers are written by `generate.py` from the FIX repository and its templates; there
  is no grammar in `src/DotGram.Finance` for the generator to read, so what it emits cannot change
  what a FIX message costs. The one place it could reach is the expression language, whose parser IS
  generated from an inline grammar and which compiles a loaded dictionary's checks — the `first
  validate` row. Its guards nest a handful deep where that change begins to matter at hundreds, so a
  difference there is not to be attributed to it either without a row built to see it.

Two things about the **instrument** changed, and they are named so that a difference from the last
file is not read as the library moving:

- **The allocation table is warmed a hundred thousand times instead of twenty.** One 32-byte object
  of our parse path is heap-allocated in tier-0 code and elided in promoted code, so a table warmed
  twenty times printed a cold number and called it the cost.
- **Our byte figures carry a resolution of one 32-byte object**, and this run shows it inside
  itself: `ours: parse + read` and `A/A ours: parse + read` are the same code under two names, and
  BDN reads 2.62 KB for one and 2.59 KB for the other on the 4.2 order — 32 bytes apart, on all
  three version rows, always with the A/A copy lower. So a 32-byte difference between two of our
  byte figures is the instrument's floor, not a cost.

## The checks, which came first and need no window

Every one of these was run before anything was timed.

**The pairing, unchanged** (the argument for it is in the 2026-09-24 file and is not repeated):
parse against parse, parse-and-validate against parse-and-validate with their **two** calls, because
their `validate` flag alone still accepts a message missing a required field and the static
`DataDictionary.Validate` is what refuses it (`--flag-check`, re-run and unchanged). Every row reads
fields, the same tags in the same order on both sides.

`--against-check`: all five 4.4 shapes, both schemas, the two sides reading identical sums, their
validating pair returning rather than throwing on valid input. `--matrix`: the seven 4.4 defects,
each caught by both sides, in the two forms they have — ours reports every finding, theirs throws on
the first.

### The new versions, and what was done to make them fair

Their side is QuickFIXn.FIX42 and QuickFIXn.FIX50SP2, each reading the dictionary its own package
ships — and, for 5.0, two of them, since FIXT 1.1 carries the session layer and FIX 5.0 SP2 the
application. That is their own arrangement, not one made for this table.

**Their 5.0 edition is later than our repository, so the wires stay off where they disagree.** Their
`FIX50SP2.xml` carries message types the 2010 Unified Repository does not and writes `UsernameGrp`
as a field where the repository has a group. None of that is in these wires.

**The zoned time is not in the paired 5.0 wire, and that is a choice with a reason.** A 5.0 order
can carry MaturityTime (1079), a TZTimeOnly, and the stand reads one that does
(`benchmarks/results/stand-fixmsg-versions-2026-09-25.md`). Here it would be dishonest in our favour
and against us at once: our field is converted as the wire is read, theirs holds text until
something asks, and their message has no accessor for a zoned value at all — so ours would pay for a
conversion nothing in the row consumes and theirs could not be made to pay for one. Every other
field in these wires is converted on both sides, which is what makes the two sums comparable:

## The dictionary, in two numbers

Ours no longer does its work in one place, so one number would flatter us. Their `DataDictionary`
builds tables at construction; ours reads a dictionary into a value, applies it, and compiles each
check when a message first asks for it.

### (a) the load

Cold: one invocation a sample, ten fresh processes, the file read once first so that neither side
pays the disk for both. Ours is
`Fix44Context.Default.With(FixDictionary.LoadFile(FIX44.xml).Merge(LoadFile(errata)))`; theirs is
`new DataDictionary(FIX44.xml)`. **Ours reads two files** — their published file does not load into
this package alone, and the errata is what reconciles it with FIX 4.4 — so a row that hid the second
file would be hiding a refusal.

| | ours | QuickFIX/n | | 2026-09-24, ours |
| --- | ---: | ---: | --- | ---: |
| time, median | **76.84 ms** | **19.47 ms** | 3.9× theirs | 697.92 ms |
| time, mean ± SD | 77.22 ± 1.87 | 26.38 ± 21.80 | | 690.51 ± 36.30 |
| allocated | **16.85 MB** | **4.85 MB** | 3.5× theirs | 252.49 MB |

**The load is nine times faster and fifteen times lighter than the day before**, and against theirs
it went from 34× and 52× to 3.9× and 3.5×. That is the lazy change, in the row built to see it.

### (b) the first validation after it

One message of each of the ten types, parsed and validated once, in a process that has done nothing
else. The dictionary is read in the setup, which is not timed. Both sides pay the runtime's first
compilation of their own code here, and that tax is not subtracted from either.

| | ours | QuickFIX/n |
| --- | ---: | ---: |
| BDN, mean ± SD over ten fresh processes | **356.64 ± 23.40 ms** | **26.31 ± 0.28 ms** |
| one process, its own stopwatch (three runs) | 397-404 ms | 28.8-29.5 ms |
| allocated, one process | **40.5-40.9 MB** | **67,032 bytes** |

**BDN's Allocated column for this row is not quoted, because it is not this row's.** Its memory
diagnoser runs iterations of its own, so in a cold row of one invocation it describes a LATER call —
one where every check is already compiled — and it reported 19 KB for work that allocates 40 MB. A
number two thousand times too small, and plausible-looking; the figures above come from one process
counting its own thread.

**What it costs is per type, and the types are not alike.** One point would have invited an
extrapolation that is wrong:

| types | ours: time | ours: allocated |
| ---: | ---: | ---: |
| 1 (a heartbeat) | 110 ms | 2.08 MB |
| 3 (heartbeat, test request, logout) | 115 ms | 2.98 MB |
| 10 (those three and an order, a logon, two cancels, an execution report, a market-data request) | 399 ms | 40.6 MB |

So about 105 ms and 2 MB is the fixed cost of compiling anything at all — the expression language's
own first call — and after that a trivial session type costs a couple of milliseconds while an order
or an execution report costs about forty and four megabytes. Theirs: 13.1 ms for one type and 28.8
ms for ten, nearly all of it the runtime compiling their code.

### What the two numbers say together

In one process, by one stopwatch: ours pays about **85 ms to load and about 400 ms over the first
ten types** — 485 ms and some 57 MB before the eleventh message; theirs pays about **28.5 ms and 29
ms**, 58 ms and 4.9 MB. So 8.4× their time and 11.6× their memory to be ready, where the load alone
read 3.9× and 3.5×.

**And the moved cost is serial where it used to be parallel.** Until `e2d8204e` the load compiled
every check with `Parallel.For` over the whole machine; now each check is compiled on the thread
that asks for it, one at a time, inside a call that is reading a message. A session meeting ten
types pays about 400 ms of that on its reading thread, in lumps of up to forty milliseconds. Whether
that is the right place for it is a design question, not a measurement, and it is the one thing in
this file worth putting to Igor.

## What may and may not be said from this

**Quotable.** Every ratio in the message tables: the smallest effect (`Binary` parse, 1.25, and the
octet `Binary`, 1.23) is eight times its row's A/A spread, and the largest are a hundred times it.
Parsing is 1.45× to 2.12× on the 4.4 shapes, 1.80× to 2.15× on the other two versions; parsing and
validating is 2.55× to 3.53× everywhere. Allocation is 1.66× to 7.02× parsing and 2.31× to 8.82×
validating.

**Not an effect.** Nothing in the message tables was inside its spread this time, which is itself
worth recording: the reason nothing had to be struck out is the window, not the library.

**Not measured, and out of the question asked.** Invalid messages (their validation stops at the
first problem and ours reports every finding — two different jobs); log framing; streaming; messages
of thousands of fields other than the group; a 5.0 dictionary loaded over our schema, which needs
its own errata and two message types removed in code; and what compiling all ninety-three types
costs, which the three sizes above say is not a straight line from ten.
