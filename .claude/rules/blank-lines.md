# Blank lines between statements in handwritten C#

The authority is `docs/coding-conventions.md`, "Blank lines between statements"; this is
the short form. It does not apply to emitted code: `*.g.cs`, `*.generate.cs`, `*.Table.cs`,
the FIX versions under `src/DotGram.Finance/Fix/Fix*/`, and any file whose first lines say
`<auto-generated` or "not edited by hand".

- A run of local declarations is one block, with a blank line before and after it.
- `if`, `for`, `foreach`, `while`, `do`, `switch`, `using`, `lock`, `try` and bare blocks
  have a blank line before and after, except directly after `{` or before `}`. `else`,
  `catch` and `finally` take none.
- Short `if`s that belong together (one-line ones, aligned as a table, or guards with their
  statement on the next line) may stand together with no blank line inside; the group as
  a whole is set apart.
- A group of short `if`s needs no blank line before a `break` or `return` only when the
  block holds nothing else (a case body of the `if`s and the `break`).
- One declaration of one variable may stand directly above its `return`; two or more may not.
- A statement after any `}` takes a blank line; a one-line `foreach` is still a control statement.
- `#if` has a blank line above it and `#endif` one below it, except next to `{` or `}`; an
  `#endif` is no separation.
- A comment directly above a statement belongs to it: the blank line goes above the comment.

`BlankLinesTests` (`tests/DotGram.Tests`) checks this against `BlankLinesBaseline.txt`. Code
you write or edit must not add a break. When a file you touched gets better, the test fails
until the baseline is lowered:

```
DOTGRAM_RECORD_BLANK_LINES_BASELINE=1 dotnet test tests/DotGram.Tests -c Release --no-build --filter BlankLinesTests
```

Commit the rewritten baseline with the change. Do not reformat code you are not otherwise
editing just to lower the counts.
