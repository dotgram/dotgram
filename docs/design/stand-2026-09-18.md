# The stand's first full run — 2026-09-18

D4 window, pinned 0-15, high priority. `--stand --rebuild` at `d4c58dfd`, `-t:Rebuild` on
every grammar-hosting project first so the generator's report table is complete rather than
whatever an incremental build happened to leave behind (Q7.4).

## What changed first

Two gaps in the stand itself, closed before this run:

- **`--rebuild`.** Reports come from `*.DotGramReport.g.cs`, and `DotGram.targets` deletes the
  old one before every compile — an incremental build that recompiled nothing left none behind.
  `--stand --rebuild` rebuilds every project that references the generator as an analyzer
  (`-t:Rebuild`, node reuse and the compiler server off) before reading them. Left out, a
  project with no report is now named in its own section of `stand.md`, with why, instead of
  the table silently coming up short.
- **Rounds/SampleMs.** The original 7 rounds of 25 ms left several fast rows at 60-120% spread
  on the hand parser — a round's batch was short enough that one OS-level jitter or GC pause
  could dominate its average. A round a generation 1 or 2 collection ran during is now redone
  rather than kept, and Rounds/SampleMs moved to 8/40: the run stays under 2x and most rows
  clear 15%. `sql/arithmetic` (62-80% across every in-budget run) and `el/interpolation`
  (30-46% regardless of Rounds or SampleMs) do not — see below.

## What tuning did and did not fix

Five runs went into picking 8/40 (`benchmarks/DotGram.Benchmarks/Stand.cs`, the comment above
`Rounds`/`SampleMs`): the original 7/25, two more at 7/25, one at 9/75 (closer to clearing every
row but 4x the run, over the ~2x budget), and 8/40 twice, including this one. Most of the rows
above settled under 15% somewhere in that sweep. Two did not:

- **`sql/arithmetic`** held 62-80% at 7/25 and 8/40 alike, four runs in agreement. One 9/75 run
  read 10% — a single sample, not a trend the other four support.
- **`el/interpolation`** held 30-46% across every run regardless of Rounds or SampleMs.

Neither looks like something a bigger sample dilutes the way the GC-pause rows did. Read as a
question for whoever profiles these next rather than chased further inside this run's budget.

## Addendum: warm-up until stable, and sql/arithmetic left open

Later the same day, architect's diagnostic (`--stand-diag`, not committed) found the cause of
`el/interpolation`'s spread: a fixed three-sample warmup left it mid-JIT-tier-promotion in some
runs — the stand keeps re-JITting new methods as later rows start, which resets the tiering
call-counting delay for whichever row is warming up. Two seconds of isolated warmup made the
step disappear outright. `3aa41f98` replaced the fixed warmup with one that runs until two
consecutive samples agree within 5% (capped at 2s, sample count kept in `stand.json`), and put
every round's time in the json too, not only its median, with the gen0/1/2 collection deltas
beside it (sql-ff) — a bimodal row is now visible from one run's json without a second,
diagnostic-only run.

Effect on the two open rows: `el/interpolation` dropped from ~40% to ~18% hand spread;
`sql/arithmetic` from ~70% to ~29% — real, but not closed.

### sql/arithmetic: open

Every hypothesis tried explains something else's spread but not this row's, tested in
isolation with `--stand-diag` (not committed) unless noted:

- **JIT tiering/OSR** — ruled out. `DOTNET_TieredCompilation=0`/`TieredPGO=0`, isolated: stable
  1546-1619ns. Isolated with tiering on, no warmup change: also stable (1187-1196ns) — the
  bimodality never reproduced in isolation at all, tiering on or off.
- **GC** — ruled out. Forced `GC.Collect()` + `WaitForPendingFinalizers()` before every round,
  isolated: stable 1184-1207ns. Per-round gen0/1/2 deltas in the committed json show gen1/gen2
  at 0 on every round that survived the redo filter.
- **CCD/core migration** — ruled out. The stand already pins to logical 0-15, one CCD on this
  machine, so migration between CCDs was never possible. Forcing the whole process onto one
  logical core (`STAND_AFFINITY=1`) in a full run made the spread worse (117%), not better —
  consistent with added single-core contention, not with removing a migration effect.
- **Instruction-cache eviction by a much larger parser** (sql-ff's theory, and the same
  asymmetry as her separate `fuzz-query.sql` D2 observation — steady on the 13.9 MB
  `SqlStandardParser` side, wandering on the ~40 KB hand-parser side) — not reproduced for this
  row. Parsing 2,000 lines of `select-items-20.sql` through `SqlStandardParser` before every
  round, normal 0-15 affinity, isolated: stable ~1210-1354ns (~11%).
- **The hand/generated round-robin itself** — not reproduced. Replicating Measure()'s exact
  alternation between `sql/arithmetic`'s own hand and generated readings, isolated: hand stable
  1200-1284ns (~7%).

What is left: the bimodality needs the full 36-row run's accumulated state to show up at all —
every isolated reproduction attempt, changing one variable at a time, came back stable. Whether
that is heap shape, thread-pool/JIT background-compilation contention from the other 35 rows, or
something else is unresolved. Per architect (2026-09-18): does not block comparisons, which are
read from medians; open until it does.
