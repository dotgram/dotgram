# The stand, every family: 2026-09-19, morning

The second baseline of every family, taken after the day's changes to the FIX reader, the
carrier choice, the value store and the corrected hand parsers for URLs. Raw data:
[`stand-2026-09-19.json`](../../benchmarks/results/stand-2026-09-19.json) and its
[`.md`](../../benchmarks/results/stand-2026-09-19.md), the twin taken with tiered PGO off:
[`pgo0-stand-2026-09-19.json`](../../benchmarks/results/pgo0-stand-2026-09-19.json) and
[`.md`](../../benchmarks/results/pgo0-stand-2026-09-19.md), and the linearity family:
[`linearity-2026-09-19.md`](../../benchmarks/results/linearity-2026-09-19.md). The evening's
[baseline](stand-2026-09-18b.md) is what the movement column below is held to.

## How it was taken

`--stand --repeat 5`, 07:38 to 08:04, from binaries built at `8b0a3b89` (main; the `Commit` of the
json is the tree the run was started from, `bc57552c`, and is not the build), on logical processors
0-15 at high priority, every other session's builds pinned to 16-31. Five runs, each in a process of
its own, the report is each reading's median. The controls of the five: 31.6, 31.8, 31.7, 31.7,
31.5 ns, so no run was dropped. The twin: `DOTNET_TieredPGO=0`, three runs, 08:05 to 08:20, controls
31.4, 31.5, 31.3 ns. Then `linearity` (rough, one run).

Rows new since the evening: the FIX slope rows in their byte and stream forms, the stock count in
its three forms and three inputs (the broken one now measures the broken path), `sql/comment`,
`sql/conditions100` and `sql/conditions1000`, `tsql/comment`. `web/url.*` are read against the
corrected `HandUrl`, so the hand's own times moved (refused: 88 to 58 ns) and a ratio over it is
not the evening's.

The base of a row is the hand-written parser; where there is none, ScriptDom (`tsql`). **All
ratios below are at the runtime's default tiered PGO.** The PGO-off column is a twin and is never
mixed with them: the hand parsers, and ScriptDom above all, slow more without PGO than the
generated ones do, so every ratio shrinks.

## Movement since the evening

- **FIX text and bytes read less** in the generated reading: on the two rows checked in nanoseconds,
  `One.text` 197 to 130 ns (-34%) and `Order.text` 1524 to 1079 ns (-29%), with the hand parser unchanged (`-1%`, `0%`): the ratio fell from
  2.2-3.1x to 1.5-2.4x on text. The stream forms moved least (2.3-3.8x).
- **SQL:2023 reads 22% less** on `sql/select20` (104,133 to 81,416 ns), hand +3%; the ratios fell by
  12-50% on every row.
- **The expression language's tape reads 8-17% more** on `el/floor`, `ladder`, `nest7`, `block`,
  `loop`, `refused-early` and `refused-late` (`ladder`: 1,759 ns in the first baseline of the 18th,
  1,877 that evening, 2,172 now) with the hand parser and the immediate carrier unchanged
  (`+0..+5%`). Not yet attributed: the baseline has more rows than the evening's and a row set
  shares one PGO profile, so the drift is either the tape's code or that profile; a paired run of
  just the `el/` rows at `2d9bd3b6` against `8b0a3b89` says which.
- **The web's generated parsers read 2-7% more** on the URL rows (refused: 459 to 570 ns, +24%),
  JSON and date-time unchanged, against hand parsers that got faster. Inside the spread of the
  URL hand rows (3-18%) except the refusal.
- T-SQL against ScriptDom and the streamed memory did not move: ScriptDom 101,627 to 101,072 ns on
  `select-long`; 4.4 KB held above the floor by both readings over 2,000,000 fields.

Spread above 20% between the five runs, so that a change on these rows is read against it: the

## Linearity

Time and allocation at three sizes each, an exponent for each ten-fold step. Flagged above 1.2:

- `stock count`, hand, text and reader (1.3-1.65): allocation is linear and generation 2 is
  collected at the largest size (0.03-0.10 a call), so it is the garbage collector: 2 MB a call
  reaches the large object heap. The generated reading is at 1.0.
- `JSON object`, generated 1.35 and hand 1.40: the same, generation 2 at 0.07 and 0.03 a call.
- `expression`, tape, 1.46 from 100 to 1,000 terms: allocation is linear (0.98) and no generation 2
  is collected, so it is the tape's own time, not the collector. Immediate is 0.98 and its time at
  1,000 terms is a tenth of the tape's (116 against 1,322 us). **A finding for the expression
  language.** The hand parser reads 1,000 terms in 140 us at an exponent of 0.25 from 100, which
  says the hand series is not a clean one at that size and is not a reference for it.
- The SQL:2023 conditions series is linear in time (0.74-0.83) and in allocation (1,578 KB at 1,000
  predicates): the quadratic allocation of the value store is gone (`e4ad4638`).
- The stock count's input with a tenth of its lines broken: generated 0.86 then 1.00 on both forms, above 1.2 only in the hand's collector-bound readings.
