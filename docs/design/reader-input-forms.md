# Additional input forms: buffered pull readers

Status: initial implementation, 2026-09-15. The design below includes future work.

## Implemented slice

- Opt-in `BufferedInput` / `BufferedBytes` compiler and host options, inherited by
  GramOptions; `parse Rule stream` / `parse Rule stream bytes` per publication.
- Additional `TryParse...` / `Parse...` overloads taking TextReader or Stream;
  existing methods keep their contracts. Where legacy Parse(TextReader) exists,
  specify bufferSize to select the new whole-result Parse overload, or use TryParse.
  Host options apply to parse, not find.
- The existing automaton lowers input checks, symbol access, and materialization
  parameters for concrete buffered character or byte readers. Contiguous scanners
  are currently disabled in these additional machines. Ordinary text emission
  retains its existing fast paths.
- Block refill, rollback across refills, owned character captures, typed values,
  guards, and character recovery. Byte roots without a declared type return byte[].
- Array reuse at proven source-independent deterministic loop boundaries; elsewhere
  retention is conservative. Capacity and logical-position limits throw IOException.
- Native byte capture spans and opt-in character capture spans; user actions own conversions.
- No async suspension, token-kind backend, or contiguous byte API yet.
  External recognizers and parserInput are diagnosed as unsupported.

The seven-element retention test parses 20,001 elements, for both character and
byte input; it validates a bounded deterministic case, not general bounded memory.
See syntax §6.3 for the implemented public contract.

## Existing implementation

`StreamingEmitter.cs` emits TextReader wrappers around span recognizers. When a
window boundary makes an answer provisional, the wrapper extends the window and
retries the occurrence or stage. Streamed parse publications depend on retention
analysis and decomposition into stages. Token-kind machines are excluded by
`Streams`. This is useful streamed result delivery, but it is not a general reader
backend for the recognition machine.

## Decision

Add a compile-time input form. Preserve the existing contiguous text form and its
fast paths. Generate a separate machine for buffered input using concrete reader
types. Share grammar analysis and recognition semantics, not a runtime interface
called for every symbol. An emitter-side abstraction is appropriate: it produces
indexing for spans and reader operations for streams.

Keep three independent dimensions:

- Symbol domain: UTF-16 characters or bytes.
- Access form: contiguous memory or buffered pull input.
- Result delivery: one final result or committed incremental results.

Reading a stream does not imply returning IEnumerable, nor does it make an entire
AST bounded in memory. Existing feed result delivery remains a separate capability.

## Publication selection

Proposed spelling: `parse Rule stream` adds a reader form to the ordinary text
publication. A generator option requests the same form for publications in a host;
publication selection takes precedence. Exact option names and byte-domain syntax
need to be settled with the first implementation. Do not overload the existing
Engine or ValueStorage options: input access is independent of both.

The publication model and machine grouping key must include the input form and
symbol domain. The generator must avoid duplicate signatures where a legacy
TextReader overload already exists. Preserve its result contract; route it through
the new backend only after equivalent continuation and recovery behavior is proven.
No silent fallback to window-and-retry when an explicitly requested form is unsupported.

## Reader operations

Use the conventional spelling Peek. A concrete generated character reader and a
concrete generated byte reader provide the same conceptual operations:

- Peek(out symbol): inspect the current symbol, filling if necessary.
- Peek(distance, out symbol): inspect ahead without advancing the logical cursor.
- Get(out symbol): consume a symbol, returning false only at actual EOF.
- Position and Restore(position): checkpoint and revisit retained input.
- ReleaseBefore(position): reclaim only input proven dead by the parser.
- Copy(from, length): produce an owned capture from retained input.

Choose one authoritative cursor; do not independently advance both a local p and
reader.Position. A position-based Peek(p, out symbol) lowering can retain the
existing local-p convention if that proves less invasive. The conceptual API above
is not a commitment to a public cursor API or a mandatory call for each operation.

The reader is sealed, owns a buffer, and performs block reads. TextReader.Read and
Stream.Read dispatch occurs on refill, not once per symbol. Short nonzero reads do
not imply EOF. Fast checks operate on the current buffered block; refill is a cold
path. Bulk literal comparison and scans should use available spans, with explicit
boundary handling, rather than expanding every operation into scalar Get calls.
Never retain a span across a refill that can replace or recycle its backing storage.
The caller owns the underlying stream; parser completion does not close it.

First implement synchronous pull: Peek waits for refill and the current machine
continues without restarting. Async and externally supplied chunks require saved
continuations and a distinct NeedMore state; bool Peek alone cannot represent those.
Do not claim that synchronous support implements resumable asynchronous parsing.

## Backtracking and retention

A checkpoint is a logical position, not a seek on the underlying stream. Restore
moves within retained storage. Lookahead uses checkpoints and never consumes input
logically. Failed alternatives restore parser values and context as before.

The earliest retained position must account for all live obligations:

- Choice, call, repetition, lookahead, and recovery states that can revisit input.
- Unmaterialized text captures and deferred factories that read source slices.
- Token extents whose source is still needed by recognition or materialization.
- Position tracking, including any previous-symbol dependency such as CRLF handling.

A successful subrule or factored prefix alone does not authorize release: an outer
alternative may still rewind before it. Atomic success removes only the choices it
actually commits. Release at proven boundaries; do not rescan the entire state arena
for every consumed symbol. Start with conservative retention and refine ownership
metadata at state push/pop or proven commit points.

Buffers may grow to the whole input for grammars with unbounded live obligations.
A configurable retention limit must report a resource-limit condition, never change
recognition or pretend to reach EOF. Whole-result allocation is measured separately.
Begin with simple reusable storage; compare segmented storage before adding its
indexing cost. Stream positions need long absolute offsets; audit the current int
state/tape positions before claiming support for inputs larger than 2 GB. Rebasing
must cover every live position or be avoided through an explicit position model.

Do not execute factories early merely to free input: guards, side effects and failed
alternatives have observable semantics. Captures escaping the parser must own their
content, or have an explicit owner lifetime. A source extent alone does not keep a
recycled buffer valid.

## Bytes and binary formats

Generate byte comparisons directly; do not decode arbitrary binary input into char.
Offer ReadOnlySpan<byte> as the contiguous counterpart of Stream. TextReader keeps
UTF-16 semantics, including existing character classes. Byte grammar validation must
reject unsupported Unicode categories, folding and out-of-range literals; encoded
text in a binary format needs an explicit encoding operation.

The recognition machinery can be shared, but terminal validation, literal encoding,
captures and diagnostics differ. Use owned byte arrays initially for escaping binary
captures. Byte positions count bytes; line and column are not meaningful by default.

A first binary example should include a magic signature, NUL and 0xFF, fixed fields,
and a payload crossing a refill boundary. Length-prefixed payloads, endian integer
reads and checksums are useful subsequent grammar capabilities; changing the input
backend alone does not implement them. A forward-only source can still require
buffered parser backtracking. A grammar proven deterministic with no pending source
captures can release consumed blocks promptly.

## Implementation sequence and acceptance criteria

1. Add publication/option plumbing and emitter-side input operations. Preserve
   existing generated text output; test selection and unsupported combinations.
2. Generate a synchronous character reader machine for a bounded initial grammar
   subset. Test literals, repetitions, alternatives, lookahead and EOF across every
   split of short inputs, including readers returning one symbol at a time.
3. Integrate rollback-safe typed values, captures, positions and recovery. Compare
   factory invocation counts and results with contiguous parsing. Add a losing
   alternative that rewinds across multiple refills and a capture held across refill.
4. Add the byte domain and both contiguous-byte and stream forms. Verify all 256
   byte values and short-read behavior without text conversion.
5. Extend retention proofs and connect existing feed publications. Test that memory
   remains bounded on a long committed feed and grows or hits the explicit limit
   for a grammar whose unresolved choices require retaining the prefix.
6. Benchmark tiny repeated calls, URL text parsing, large SQL/ExpressionLanguage,
   long feeds and binary inputs. Measure throughput, allocations, peak retained
   input, first-result latency, generated source and IL. Keep ordinary text output
   unchanged unless a separately measured improvement justifies a change.

Build emitted code at the existing C# 8/framework floor. No runtime package or modern
static-interface mechanism is required for this design. Performance remains an
experimental question; concrete calls make inlining possible but do not guarantee it.

## Compatibility evidence

The generated SQL92, SQL Standard, MSSQL and located MSSQL source files are
byte-for-byte identical to the saved pre-buffered implementation. Attribute support
adds the two new opt-in properties. Existing parser snapshots also remain unchanged
by this feature. Both new input forms compile at C# 8 for netstandard2.0, net472
and net8.0. Throughput of the new forms has not been benchmarked yet.

## Native semantic-action captures

Byte-form raw captures and `parserText` now use `ReadOnlySpan<byte>` throughout
materialization and action/guard calls. Character actions can opt into
`ReadOnlySpan<char>` with `SpanCaptures`; the old string contract remains the
default. User overloads perform conversions directly. Contiguous captures borrow
buffer slices; disjoint repeated captures join into an array of the input element
type. No input decoding or whole-input string is needed by this mechanism.

The buffer release proof also accounts for `parserText`, even when there are no
named captures. Source cannot be discarded before deferred actions inspect it.
This remains whole-parse materialization, not a general per-message release proof.
The FIX finance framing adapter is separate and still uses the source-owning
string model; migrating its external raw-data recognizer and public model is not
part of this generator change.
