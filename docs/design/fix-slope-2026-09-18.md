# FIX: initialization against a field — 2026-09-18

D13 (Igor, via the architect): where the generated FIX parser's gap to the hand-written one
sits — in what a parse costs before it reads a field, or in what each field adds. The stand
now carries `fix/slope-N.text` rows for N = 0, 1, 2, 4, 8, 16 fields (string form, the same
field `55=ABC\x01` repeated N times), generated and hand read together in every round like
every other FIX row, and the fit below is what they answer.

Clean, announced window, pinned 0-15 at high priority, control 30.2 ns, `27b1f60e` plus the
slope rows. Raw data:
[`fix-slope-2026-09-18.json`](../../benchmarks/results/fix-slope-2026-09-18.json).

## Fit

Least squares, value = intercept + slope × N, over all six points:

| | intercept | per field | R² |
| --- | ---: | ---: | ---: |
| hand, time | 27.2 ns | 50.99 ns | 0.9994 |
| generated, time | 72.0 ns | 131.28 ns | 0.9995 |
| hand, allocation | 202.5 B | 113.3 B | 0.9980 |
| generated, allocation | 90.1 B | 112.6 B | 0.9988 |

The empty input (N = 0) sits below the line for both parsers — hand 19.3 ns against 27.2 fitted,
generated 51.9 against 72.0 — which reads as an early-out for no input at all rather than a
fixed cost that every parse pays. Fitted over N ≥ 1 alone the intercepts are hand 30.9 ns and
generated 81.2 ns, the slopes 50.66 and 130.44 ns per field.

## What it says

- **The gap is not initialization against a field.** It is about 2.6x on both parts: 72 against
  27 ns fixed, 131 against 51 ns per field. The generated / hand ratio is flat at 2.5-2.7x from
  one field to sixteen, which is what two lines with the same ratio of slope and intercept look
  like.
- **It is not memory.** Both parsers allocate the same per field (about 113 B, one `FixField`
  each) and the generated parser allocates less to start with (90 against 203 B). What the
  generated parser spends beyond the hand-written one is about 80 ns of CPU per field.
- So a fix that removes fixed cost alone can close at most the difference in intercepts, about
  45 ns of a 2,165 ns parse of sixteen fields; almost all of the gap is per field.

## Addendum: the ideal reader (performance-ff, 2026-09-18)

`ideal`, on the same six rows, agreeing with the hand parser field by field. It is an ideal and

- Against the ideal the generated parser is 3.3x per field (140 against 42 ns) and 4.7x on the
  fixed part (85 against 18 ns); the ideal is about 0.70x of the hand parser from one field on.

- This run was made on `main` with the compact `FixField` header, so the allocation columns sit
  below the ones above. The hand parser was also about 15% slower than in the first run (58.3
  against 51.0 ns per field) at the same control, so lean on the ratios (generated / hand 2.3-2.4x,
  it was 2.5-2.6x), not on the absolute nanoseconds.
